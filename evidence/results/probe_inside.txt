LOOKING INSIDE: THE ANSWER IS NOT HIDDEN AT 4 PAIRS, IT IS ABSENT
evidence/probe_inside.py. Linear probe from the hidden state at the QUERY position to the
correct value, fitted on held-out data at every depth. A linear probe reads whatever is
linearly present, so probe >> model means the readout is the bottleneck, and probe ~ model
means the model is already extracting all there is.

  2 pairs s1   0.022   0.172   0.147   0.987   0.987   0.987      0.990
  4 pairs      0.026   0.034   0.036   0.250   0.245   0.248      0.245

TWO FINDINGS.

1. BINDING IS LOCALISED. At 2 pairs the association is absent through all of layer 0 and
   appears in LAYER 1'S RECURRENCE, 0.032 -> 0.998. Replicated on a second seed
   (0.172 -> 0.987). Not the embeddings, not the feed-forward, not layer 0. One site.

2. AT 4 PAIRS IT IS NOT THERE AT ALL. The probe reads 0.250 -- equal to the model's own
   accuracy and equal to set-guessing. The readout is extracting everything the state
   contains. The state simply does not carry the key-value association.

So the bottleneck is not the readout, and "present but unreadable" is ruled out. Every fix
aimed at extraction would have been aimed at the wrong component.

WHY, FROM THE MECHANISM. The recurrence is a linear update on ONE vector, so the state is a
superposition h = sum_i A_i c_i. At read time exactly two things are available: the query
token's transport T_q, and a fixed linear readout W. The output is

    W T_q sum_i A_i c_i  =  sum_i (W T_q A_i) c_i

and correct retrieval needs W T_q A_i ~ 0 for every i != q. That is ONE linear operator
annihilating every non-matching item: a single matched filter, which extracts ONE component.
Not a tuning constant -- a consequence of one vector and one query-dependent operator.

Given the value set is known (in_set ~ 0.9), the assignment entropy is log2(n!):

    n=2  1.00 bits   n=3  2.58 bits   n=4  4.58 bits   n=8  15.30 bits

n=2 needs exactly ONE BIT and one matched filter delivers exactly that. n=4 needs 4.58 and
gets none, which is why it lands exactly on set-guessing rather than degrading partway.
Two pairs sits precisely at the structural limit, which is why it looked like success and
generalised to nothing.

REGISTERED PREDICTION, before the run: n=3 needs 2.58 bits, already past one filter's
budget, so it should COLLAPSE to ~0.333 rather than landing near 0.7. A cliff supports the
arity account; a graceful slope refutes it and points back at capacity. Run in progress.

WHAT THE SESSION WAS MISSING, SETTLED

The limit is not how MUCH the state holds -- not holonomy, not signatures, not the Birkhoff
polytope, not the trace law's overlap. Those all measure capacity. The limit is ARITY: how
many items can be SELECTED at read time.

The recurrence writes one vector, so the state is a superposition sum_i A_i c_i. At read
time only the query's transport T_q and a fixed readout W exist, so the output is
sum_i (W T_q A_i) c_i and retrieval needs W T_q A_i ~ 0 for every i != q. One linear
operator annihilating every non-match is ONE MATCHED FILTER, and one filter extracts one
component. Given the value set is known (in_set ~ 0.9), the assignment costs log2(n!) bits.
One filter buys about one. n=2 needs exactly one and is perfect; everything above gets
nothing, and gets nothing the same way.

WHY EVERY FIX FAILED
  n_h 2 -> 8          reshapes the filter, does not add a second one
  carving             protects a superposition that was never the problem
  level-2 on output   the bottleneck is what the recurrence WRITES, not how it is read
  optimiser (muon)    reaches the one-bit solution 10x sooner; cannot manufacture a 2nd bit

WHAT WOULD FIX IT: a read-time comparison against every stored key at once -- keys in
separate addressable rows rather than summed into one vector, so retrieval is a contraction
against rows instead of one filter against a sum. That is a matrix state, and it is what
softmax(q^T K)V does. The level-2 idea was right in kind and wrong in placement.
